## [0.1.0] - 2026-09-27

Первый выпуск. Плагин появился после удаления `@wingsky-1/dsh-mcp-manager` (тот согласовывал
видимость инструментов вызовами ядрового `tools.restrict()` **для каждого имени инструмента**, каждый вызов
пересчитывал весь registry view и доводил web-хост до CPU 94.7% / порт без ответа 8 секунд / JS-куча 1080 MB).

### Возможности

- **Добавление / удаление / включение-выключение MCP-серверов в рантайме**, без перезапуска DSH. Два транспорта:
  stdio (`command`/`args`/`env`/`cwd`) и Streamable HTTP (`url`/`headers`).
- **Панель «Управление MCP» на веб-странице настроек**: живой этап, число инструментов и их имена, тест подключения
  (черновик не сохраняется), включение/выключение, редактирование, удаление, импорт из старого менеджера, перечитывание конфигурации.
- **8 инструментов agent**: `mcp_manager_status` / `list` / `add` / `update` / `remove` / `test` / `import` / `reload`.
  Удаление — в два шага: без `confirm` выполняется только предпроверка.
- **Конфигурация в `$DSH_HOME/dsh-mcp-manager.json`** (0600, учитывает `DSH_HOME`, атомарная запись).
  Формат на диске совместим с `mcp-manager-mcp.json` старого менеджера — можно импортировать напрямую.
- **Два независимых переключателя**: установки (строка композиции профиля) и рантайма (файл конфигурации / панель); семантика описана в README.

### Архитектура

- **Собственная реализация MCP не пишется** — через `ctx.plugin()` динамически подключается штатный
  `@deepseek-ai/dsh-mcp-client` из harness: один экземпляр на включённый сервер, отключение = `fiber.dispose()`.
  Транспорты, очистка учётных данных, повторные подключения с задержкой, публикация ресурсов и договор об именах
  берутся из ядра целиком.
- **Ядровый `tools.restrict()` не вызывается нигде**. Единственное чтение реестра — один `ctx.tools.schemas()`
  на каждое наблюдение + группировка в памяти по префиксу; затраты линейны.
- **Разрешение моста — лестница**: сначала копия работающего harness (realpath от CLI-входа), потом farm ссылок профиля, и лишь затем дерево зависимостей самого плагина; `/probe` сообщает, какая ступень использована.
- Все точки входа хостовой половины обёрнуты в обработку исключений: не подключившийся MCP-сервер или отсутствующий мост не роняют web-boot.

### Исправления (пойманы end-to-end проверкой в процессе разработки)

- **Переключатель «Отключить плагин» раньше был декоративным**: панель писала `enabled` в файле конфигурации,
  а рантайм читал `enabled` из строки композиции — переключение ничего не меняло, все серверы оставались подключёнными. Теперь оба переключателя независимы и работают; семантику фиксируют 11 целевых регрессионных тестов (`tests/manager.mjs`).
- **`snapshot()` раньше шорт-катился в «все stopped», если файл состояния ещё не читался**, из-за чего любой
  вызывающий код, не запускавший `initialize()` (включая панель при медленном старте), видел мёртвую машину. Теперь состояние всегда вычисляется по факту.

### Проверки

- `npm test`: 54 unit-теста (модель определений / персистентность и 0600 / рантайм: группировка и этапы /
  семантика двух переключателей / лестница разрешения моста / маршруты loopback и охрана).
- `npm run verify:live`: end-to-end на реальном изолированном экземпляре — конфигурация → мост → настоящий stdio MCP-сервер (рукописный fixture без зависимостей)
  → инструменты `mcp__echo__*`; затем через HTTP добавление / отключение (инструменты снимаются сразу) / удаление / пробный запуск черновика / главный переключатель — всё без перезапуска.
- `npm run verify:full`: гейт переносимости (изолированный `DSH_HOME` + установка из tarball + маршрут здоровья + клиентский bundle).
