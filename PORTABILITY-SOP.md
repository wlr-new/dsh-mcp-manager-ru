# SOP проверки переносимости dsh-mcp-manager

> Источник правила: `~/.dsh/AGENTS.md`, раздел 10 (действует без условий). Критерии: `2️⃣ AI/Standards/DSH插件可移植性验证清单.md`.
> Инструменты: `DSH /DSH-test/dsh-release-kit/` (`portability.mjs` скопирован в `scripts/` этого репозитория).
> **Гейт: публиковать можно только после `✅ Пройдено`.**

## Почему этому плагину это особенно нужно

Суть плагина — **запускать чужие MCP-серверы как дочерние процессы на чужих машинах**, поэтому у него есть три класса риска, которые взрываются только не на вашей машине:

1. **Разрешение MCP-моста.** Плагин сам протокол не реализует — он управляет штатным `@deepseek-ai/dsh-mcp-client` из harness
   (лестница разрешения в `src/core-mcp.ts`). Найдёт ли этот пакет после установки из tarball — корневая причина «установилось, но ни к одному серверу не подключается».
2. **`DSH_HOME`, а не `~/.dsh`.** Файл с определениями серверов обязан лежать в home самого harness; захардкоженный `~/.dsh` заставит машину с перенесённым home читать пустой список, тогда как настоящая конфигурация лежит в другом месте.
3. **Отсутствие файла при проверке.** Маршрут здоровья должен честно отвечать и при **нулевой конфигурации**, иначе «чистая машина» будет ошибочно признана сломанным плагином.

## 1. Стандартные действия (перед каждым релизом)

```bash
npm run verify:full          # = node scripts/portability.mjs --health /api/dsh-mcp-manager/probe
npm run verify:live          # end-to-end на реальном экземпляре: конфигурация → настоящий MCP-сервер → инструменты mcp__*
```

Восемь шагов, всё автоматически; код выхода — и есть вердикт:

| # | Шаг | От чего защищает |
| --- | --- | --- |
| 1 | Статическая проверка | абсолютные пути этой машины / платформенные команды без проверки платформы / запись в `.dsh` без учёта `DSH_HOME` |
| 2 | `npm pack` + сверка точек входа | файлы из `main`, `exports["./client"]`, `dsh.bundle.patch`, `files` не попали в пакет |
| 3 | Чистая установка | пустой профиль + **tarball** (не `link:`); установилось — и попало ли в `dsh.profile.bundles` |
| 4 | Запуск | экземпляр в **изолированном `DSH_HOME`** + отбор строк с ошибками из вывода запуска |
| 5 | Хостовая половина | действительно ли отвечает `GET /api/dsh-mcp-manager/probe` |
| 6 | Клиентская половина | объявление `dsh.client`, id регистрации bundle **равен ли имени пакета**, есть ли он в `__DSH_BOOT__.entries` |
| 7 | Реальное действие | у плагина нет интерфейса перезапуска — пропускаем (реальные действия берёт на себя `verify:live`) |
| 8 | **Наблюдение за стабильностью** | **жив ли экземпляр после готовности** (поздний срыв = ложный успех) |

> «Реальное действие» для этого плагина — `npm run verify:live`: в изолированном экземпляре реально
> запускается stdio MCP-сервер, проверяется, что инструменты зарегистрированы как `mcp__<name>__*`, а затем через HTTP
> прогоняются добавление / отключение / удаление — доказательство «без перезапуска».

## 2. О маршруте здоровья плагина

`/api/dsh-mcp-manager/probe` **возвращает 200 даже при выключенном плагине** (просто сообщает `enabled: false`).
Это сделано намеренно: он служит health-check гейта переносимости, и «выключенный плагин» с кодом 503 был бы прочитан как «установка сломана».
Он же выводит оба переключателя, чтобы отличить «выключили специально» от «сбой запуска»:

```json
{ "ok": true, "enabled": true, "masterSwitch": true, "serving": true,
  "servers": 0, "toolCount": 0, "managerTools": ["mcp_manager_add", "..."],
  "bridge": "harness", "bridgeError": null }
```

- `bridge`: `harness` / `profile` = используется штатный мост harness; `bare` = паление в дерево зависимостей самого плагина (версия могла разъехаться).
- `managerToolCount`: единственный наблюдаемый признак того, что инструменты agent действительно смонтированы (они живут в реестре инструментов, а не за маршрутами).

## 3. Ручная сверка

```bash
npm pack
export DSH_HOME=$(mktemp -d)/dsh-home                      # ① изоляция обязательна
dsh --profile verify-mcp-mgr --from-default-profile web --dump-config
dsh plugin --profile verify-mcp-mgr add "file:$PWD/zhengjunyao-dsh-mcp-manager-0.1.0.tgz"
python3 -c "import json;print(json.load(open('$DSH_HOME/profiles/verify-mcp-mgr/package.json'))['dsh']['profile']['bundles'])"
dsh --profile verify-mcp-mgr --port 3456 --no-open > /tmp/verify.log 2>&1 &
grep -n "Error\|error:" /tmp/verify.log                    # ② LISTEN на порту ≠ успешный запуск
curl -s http://127.0.0.1:3456/api/dsh-mcp-manager/probe    # ③ хостовая половина
TOKEN=$(grep -o 'token=[A-Za-z0-9_-]*' /tmp/verify.log | head -1 | cut -d= -f2)
curl -s -L -c /tmp/ck -b /tmp/ck "http://127.0.0.1:3456/?token=$TOKEN" -o /tmp/idx.html
grep -c "@zhengjunyao/dsh-mcp-manager/client.js" /tmp/idx.html    # ④ клиентская половина
sleep 15 && curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3456/api/dsh-mcp-manager/probe   # ⑤ ещё жив?
lsof -ti tcp:3456 -sTCP:LISTEN | xargs -r kill; rm -rf "$DSH_HOME" *.tgz
```

## 4. Четыре ловушки, о которых нужно знать

1. **`DSH_HOME` изолировать обязательно.** Второй экземпляр на той же машине ждёт блокировку записи `~/.dsh/.credentials.yaml` до тайм-аута
   (`atomic-write: timed out waiting for the writer lock`) и не стартует — без изоляции весь результат проверки ложный.
   Поэтому `verify:live` этого плагина **никогда не трогает настоящий `~/.dsh`**.
2. **LISTEN на порту ≠ успешный запуск.** `dsh web` сначала привязывает порт, а потом грузит дерево плагинов; сбои вроде тайм-аута блокировки учётных данных вылезают через ~30 секунд.
   Поэтому нужно смотреть и строки ошибок в выводе запуска, и понаблюдать за экземпляром после готовности.
3. **Строка URL с токеном приходит поздно, а pipe её не удержит.** `dsh web` форкает настоящий сервисный процесс; когда wrapper завершается, pipe закрывается, и токен, написанный форкнувшейся половиной, теряется — поэтому инструмент пишет stdio в **файл**.
4. **Проверка доказывает только «на чужой машине ставится и стартует»**, но не «подключается к чужим MCP-серверам» — это зависит от самого сервера. Контракт плагина: **если конфигурация верна — подключение установлено, если нет — ошибка честно сообщена, а запуск harness не пострадал**.

## 5. Вето (любой пункт — и релиз останавливается)

1. В исходниках есть абсолютные пути этой машины.
2. Объявленные точки входа / файлы, загружаемые в рантайме по путям, не попали в пакет.
3. После установки tarball в пустой профиль плагин отсутствует в `dsh.profile.bundles`.
4. В выводе запуска есть ошибки (даже если порт отвечает).
5. ID регистрации клиентского bundle не совпадает с именем пакета.
6. В `__DSH_BOOT__.entries` нет `@zhengjunyao/dsh-mcp-manager/client.js`.
7. После реального действия сервис не вернулся (для этого плагина эту роль выполняет цикл добавление/отключение/удаление в `verify:live`).
8. **Не продержался после готовности** (в окне наблюдения маршрут здоровья отвалился / процесс заменили / появились новые фатальные строки запуска).

## 6. После прохождения

1. Вывод `npm run verify:full` — `✅ Пройдено`, вывод `npm run verify:live` — `✅ Проверка на реальном экземпляре пройдена`.
2. Вердикт заносится в досье проекта (пройдено / не пройдено + проваленные пункты).
3. Дальше версионная дисциплина → git tag → npm publish → агрегаторы.

> Порядок важен: **переносимость проверяется до версии**. Номер можно выпустить заново; а то, что чужие не установят, — это «опубликованное сломано».
